## ADR-013 Effective model computed in Go from current main
A draft's effective model is the current main snapshot plus the draft's active changes, applied in memory by `changeset.State` (whole model loaded; fine for MVP sizes). Main tables hold only current state, so reads "at base_version" of an older main are not possible yet; M2 rebases / merges and reconstructs history for `/versions/{n}`. Chosen over an SQL-side overlay for testability and simplicity (brief: "keep simple, optimize later").

## ADR-014 Undo/redo: `changes.undone_at` + `batch_id`
Added to the brief's `changes` schema. One GUI edit = one batch; undo marks the latest active batch undone, redo clears the most recently undone one, recording a new batch deletes the undone tail. Undone rows are ignored by the effective model and kept as audit trail until the tail is replaced. Rejected alternative: delete-on-undo with an in-memory redo stack (loses redo on restart, no audit).

## ADR-015 Change payload semantics
`add`: normalized full entity; ids are server-generated UUIDv7 unless the client supplies one (needed to reference new entities inside one batch). `update`: only changed fields; `before` holds their old values. `delete`: `before` holds the full snapshot. Cascading deletes (descendants + relations touching deleted elements) are expanded into explicit delete changes so the future diff shows exactly what is removed; deleting an element with children without `cascade: true` is a 400.

## ADR-016 Structural validation now, business rules in lint (M2)
Services reject malformed edits (kinds, blank names, missing targets / parents, parent cycles, relation endpoints, server-managed fields in patches). Hierarchy rules, duplicate siblings / relations and protected-element rules are lint / merge concerns (M2) and are NOT enforced while editing a draft.

## ADR-017 Domain errors and interim actor
`internal/platform/apperr` (invalid / not found / forbidden / conflict / unauthenticated) has no Echo dependency; `httpx` maps them to problem+json (supersedes the "implement echo.ProblemErrorer in transport" note of ADR-005). Role checks live in services via `authctx.Actor` in the context. Until session auth exists, `AUTH_DEV_HEADER=true` enables an `X-Dev-User: <email>` header that resolves a seeded user; it is off by default and logged loudly when on. (The header part is superseded by ADR-054.)

## ADR-018 Seed bootstraps main through `changeset.Bootstrap`
Main is read-only via the API, so the sample model is created by a maintainer-only `Bootstrap` that records a merged changeset, its changes and `model_versions` row 1, and materializes through the same `MaterializeChanges` the M2 fast-forward merge will use. It refuses to run once a version exists (seed treats that as "already seeded").

## ADR-019 Integration tests: shared container, DB per test, no goose library
`internal/testdb` starts one `postgres:18` testcontainer per test binary and creates a fresh database per test, applying the `-- +goose Up` sections of `db/migrations` directly (goose is not a library dependency, see ADR-009). Tests skip under `-short`. sqlc generates one package per feature (`user`, `model`, `changeset`) from `db/queries/*.sql`, with `uuid` -> `google/uuid` and `timestamptz` -> `time.Time`.

## ADR-020 Version history = full snapshots (supersedes ADR-013's "no history yet")
Every merge stores a JSON snapshot of main in `model_snapshots` (one per `model_versions` row; migration 00003 backfills the current version). A draft's effective model is now **snapshot(base_version) + its active changes**, as the brief specifies, so a stale draft keeps showing the world it was based on until it is rebased by a merge. Snapshots give the 3-way merge its base, `/versions/{n}/model` its data, and version diffs for free. Chosen over replaying merged changes because a rebase rewrites what actually reached main (resolved conflicts, dropped dangling entities), which a change log of the original draft would not reflect. Cost: storage grows with model size x versions; acceptable for MVP and prunable later.

## ADR-021 Merge: field-level 3-way rebase with explicit resolutions
`Merge3(base, mine, theirs, resolutions)` is a pure function. Per target: untouched on one side -> take the other; both modified -> per-field merge (disjoint fields and identical values auto-merge); same field with different values -> `field` conflict; delete vs update -> `delete_vs_update` conflict; entities left referencing something the merge removed (new child under a parent the other side deleted, relation to a deleted element) -> `dangling_reference` conflict. A resolution is `mine` or `theirs` per (target, field or `*`); for dangling references it means "whose world wins": restore the referenced entity from that side, or drop the dependent entity (and its dependents) if that side deleted it. Resolutions are stored (`merge_resolutions`) so conflicts can be resolved incrementally via `POST /resolve` and survive restarts. Conflicts return `409` with the conflict list and change nothing. When main has not moved (`current == base_version`) the merge is a fast-forward. Merges are serialized by a transaction-scoped advisory lock (`LockMain`); the merged result is applied to main as add / update / soft-delete changes derived from `diff(theirs, result)` and then snapshotted.

## ADR-022 Review workflow and roles
`draft -> in_review` (submit: author or maintainer) `-> merged` (maintainer) | `rejected` (maintainer) | `abandoned` (author or maintainer, from draft or review). `approve` is a recorded maintainer sign-off (`approved_by/at`, cleared on resubmission) that merge requires; the brief's statuses stay unchanged. A maintainer cannot approve or merge their own changeset unless `MERGE_ALLOW_SELF=true` (default `false`). Changesets in review are frozen (no edits); rejected / abandoned / merged ones are terminal. Lint **errors block merge** (`409` problem), warnings do not.

## ADR-023 Protected elements
Interpretation of "protected elements change only via an in_review changeset merged by a maintainer": every change already goes through that path, so we add two guards. (1) Only maintainers can set or clear the `protected` flag in a draft. (2) A changeset that modifies or deletes a protected element (relative to its base) must be approved and merged by a maintainer other than its author, even when self-merge is enabled (four-eyes). Both are enforced in the service layer and covered by unit and integration tests.

## ADR-024 Lint rule engine
`internal/lint`: `Rule{ID, Check(Snapshot)}` over the effective model; findings carry rule, severity, message and target. Errors: parent-kind hierarchy (component under container, container under system, node under node; person / system are roots; container / component require a parent), relation endpoints exist, `deployed_on` goes container / component -> node, no duplicate (source, target, kind), no duplicate sibling names (case-insensitive). Warnings: orphan (no parent, children or relations; person / system exempt), `uses` without technology, container / component without `deployed_on`. The merge re-runs lint on the merged result, not only on the draft.

## ADR-025 Canvas: React Flow nested nodes + ELK, layout kept out of the model
`@xyflow/react` 12.12.0 renders the hierarchy with `parentId` sub-flows (parents before children, children `extent: "parent"`); `elkjs` 0.12.0 (bundled build, main thread: the seed-sized graphs lay out in a few ms) computes a compound `layered` layout (`hierarchyHandling: INCLUDE_CHILDREN`, direction RIGHT), whose child coordinates are already parent-relative like React Flow's. Collapsed elements are fixed-size cards (232x96) so layout needs no DOM measuring. Pure logic (tree, visibility, edge aggregation, filters, ELK adapter, tween math) lives in `features/canvas/*.ts` with vitest unit tests; React components only render. Model and layout stay separate: dragging writes only `positions` in a Zustand store (ephemeral; persisting layout per view is M5) and never the model; ELK positions apply to everything not dragged.

## ADR-026 Semantic zoom, expand / collapse and edge aggregation
Expanded set lives in the canvas store. Double-click or the chevron toggles a node; "Expand all / Collapse all" refit the view. Semantic zoom: when a pan / zoom ends, any collapsed node with children that is on screen and wider than 340 px expands in place (expand only; collapsing stays explicit so the view never jumps). Relations touching a collapsed element are re-routed to its nearest visible ancestor and parallel relations between the same pair become one edge with a count badge (dashed when only `deployed_on`); relations inside one node, or between a node and its own descendant, are not drawn. Layout changes are tweened in JS (280 ms ease-out) rather than via CSS transitions so nodes and the edges attached to them move together; new nodes fade in; `prefers-reduced-motion` applies changes immediately and disables the BorderBeam (which only appears on a selected protected node).

## ADR-027 Element tree, filters and property panel
The tree is a WAI-ARIA `tree` (roving tabindex, arrows / Home / End / Enter) with search, kind toggles and tag chips. While a filter is active the tree shows matches plus their ancestors and the canvas dims non-matches (the canvas structure does not change). Selecting in the tree "reveals" the element: expands its ancestors, selects it and centers the canvas after the layout animation. The property panel is read-only in M3 (real form controls, ready for M4 editing inside a draft).

## ADR-028 TechIcon resolution
`components/tech-icon`: custom upload (prop, wired in M6) -> simple-icons (monochrome, `currentColor`) -> colored logos (devicon-style fallback via `@iconify-icons/logos`) -> lucide `Box`. A case-insensitive alias map normalizes free text ("k8s", "Node.js", "PostgreSQL 16", "Go / Echo": each word is tried). Icons are statically imported in `icons.ts` (bundled, offline-safe, tree-shaken subset). Dark colored logos are rendered as light silhouettes in dark mode. Kinds use lucide icons.

## ADR-029 Browser auth in dev, UTC timestamps, test tooling
The Vite dev proxy adds `X-Dev-User: $DEV_USER` (default `viewer@archmap.local`) to `/api` requests, matching the API's `AUTH_DEV_HEADER` stand-in until session auth exists (superseded by ADR-054: the header, `DEV_USER` and the user switcher are gone). The API now emits all timestamps in UTC (`Z`): the generated Zod `datetime` validators reject numeric offsets like `+08:00`, which the first real browser run exposed (regression test in the API's HTTP e2e suite). Web unit tests use vitest 5 (`pnpm --filter web test`, part of `task test` and CI) in a node environment; the canvas was verified visually in headless Edge (dark / light) against a live API.

## ADR-030 Draft editing: every GUI edit is one batch through the existing API
Add / edit / delete / connect all call `POST /changesets/{id}/changes` with one batch per user action (so undo / redo, the history feed and the audit trail line up with what the user did). Forms (`ElementDialog`, `RelationDialog`) only build change inputs (`patches.ts`, unit tested: an edit sends only the changed fields; the protected flag is sent only by maintainers); element ids are generated client-side (`crypto.randomUUID()`) so the canvas can reveal a new element immediately. Deleting an element with children sets `cascade` after an explicit confirmation that states how many nested elements and relations go with it. Edit mode exists only for a draft the user may edit (author or maintainer, status `draft`); everything else is read-only (`workflow.capabilities`).

## ADR-031 Optimistic updates are UI previews, not domain logic
Mutations patch the cached effective model (`optimistic.ts`: shallow merge / remove only, no validation) so the canvas reacts instantly; any rejection restores the previous cache and shows the API's problem detail as a toast, and every settled mutation refetches the model, diff, lint and conflicts. Hierarchy hints in the forms (`kindRules.ts`) only narrow the choices offered; the API's lint rules stay authoritative.

## ADR-032 Review surface: diff overlay, lint panel, conflicts, history
`GET /diff` drives a canvas overlay (added green, modified amber, removed red ghosts that are merged into the displayed tree, edges colored from their relations) plus a field-level diff list. `GET /lint` drives per-node error / warning markers, a findings list that reveals the target, and error / warning counters (Magic UI `NumberTicker`) in the draft bar. Merge conflicts (`409` + list) open the Conflicts tab with base / mine / theirs and a keep-mine / keep-theirs choice per conflict, then `POST /resolve`, then merge again. The change log is shown grouped per batch (Magic UI `AnimatedList`), undone batches struck through.

## ADR-033 Review workflow UI and roles
The draft bar shows only the transitions the status allows (`workflow.workflowActions`): submit and abandon for author / maintainer, approve / reject / merge (after approval) for maintainers. Disabled actions carry a reason; the API remains the authority (self-merge flag, protected-element four-eyes) and its refusals surface as toasts. Routes: `/` (main, read-only, "New draft"), `/changesets` (list with status filter), `/changesets/$id` (draft workspace).

## ADR-034 Dev user switcher and connection UX
In dev the top bar has a user switcher (viewer / editor / maintainer) stored in localStorage and sent as `X-Dev-User` by an API-client request interceptor (the Vite proxy only fills in `$DEV_USER` when the browser sent none). Connecting: drag from a node's handle, or drop anywhere on another node (the drop target is found with `elementsFromPoint` because React Flow's connection overlay swallows the event target); a dialog picks the relation kind, technology and description. The shell consistently uses only server data during SSR (a localStorage read in render caused a hydration mismatch). Changeset lists show the author as "You" / a short id because the API has no users endpoint yet. (The user switcher and `X-Dev-User` are superseded by ADR-054: development uses the dev sign-in provider.)

## ADR-035 Canvas context menu
Right-click opens a menu for the element, the relation (edge) or the background (`CanvasContextMenu`: the shadcn dropdown menu anchored to an invisible point, so arrow keys, Enter, Escape and submenus work). View entries are always present (expand / collapse, zoom to element, expand all, collapse all, fit, reset layout); inside an editable draft the page adds edit entries built by pure functions (`draft/menuEntries.ts`, unit tested): element -> Edit, Add child (only kinds valid under that parent), Connect to…, Delete; relation -> Edit / Delete (an aggregated edge first lists its relations); background -> Add element (top-level kinds). Removed (ghost) elements get no edit entries. "Connect to…" enters a connect mode (banner, crosshair cursor, Escape cancels): the next element clicked becomes the target and opens the same relation dialog as dragging a connection, so there is a keyboard / pointer-light alternative to dragging.

## ADR-036 Views live beside the changeset workflow
Views (`views`, `view_elements`) are saved perspectives, not model: creating, editing or laying one out creates no changes and no versions, needs no review and is shared by main and every draft (editor+ writes; renaming / deleting needs the creator or a maintainer; saving layout is open to any editor, last write wins). A view therefore never goes through diff / merge. `view_elements` rows may reference elements that do not exist in the model being shown (draft-only elements, deleted ones): readers ignore them, and the web client passes unknown entries through when it saves so a save from another context does not erase them. The integration test asserts that views and layout saves leave elements, relations, versions and changesets byte-identical.

## ADR-037 View membership is computed on the server
A view shows a set of **roots** plus all their descendants; a root's parent is not in the result, so the canvas treats it as top-level, expands it in place and rolls relations up with the existing aggregation. `view.Compute` (pure, table tested) decides the roots: landscape = top-level people and systems; context = scope plus the people / systems it talks to (top-level ancestors of the other end of `uses` relations crossing the scope's boundary); container and component = scope plus the highest ancestor of each other end that does not contain the scope (so a sibling container is a neighbour, its parent system is not); deployment = top-level nodes (or the scope node) plus what is deployed on them via `deployed_on`; custom = the saved members. Scoped container / component views start with the scope expanded, deployment views with the node tree. A scope that does not exist in the model being shown yields `scope_missing` instead of an error. `GET /views/{id}/model?changeset_id=` computes from main or from a draft's effective model (`apiserver.ViewModelSource` joins model and changeset so those features stay independent of views); membership rules are domain logic and stay in Go.

## ADR-038 Layout persistence
Layout is `x`, `y` (relative to the parent node), `w`, `h` (reserved) and `collapsed` per element, saved with `PUT /views/{id}/layout` as a full replacement of the view's layout (custom membership is untouched). Only moved or expanded elements are stored (collapsed and un-moved is the default; rows that carry nothing are pruned). The canvas store counts user layout changes (`revision`); `useViewWorkspace` loads a view's layout once when it is opened (draft edits that refetch the view do not overwrite local moves), autosaves 700 ms after the last change, flushes on view switch and page hide, and only for editors (a viewer's moves are a local preview). A view that was never laid out starts from the server's default expansion. "Whole model" has no stored layout. Switching views remounts the canvas so it refits.

## ADR-039 View UI
A tab strip above the canvas (`ViewTabs`) on main and on draft pages: "Whole model" plus the saved views, "+ New view" and a per-view menu (edit, delete). The selected view lives in the URL (`?view=`), so it is linkable and survives reloads. `ViewDialog` creates / edits a view: kind, scope picker (filtered to the kinds the view kind accepts), name, description and, for custom views, a filterable member checklist. In a draft, the selected view is computed from the draft's effective model, so new elements appear in views that would include them (a new child of a visible scope, a new top-level system in the landscape); removed-element ghosts of the diff overlay are shown only in "Whole model".

## ADR-040 Layers: an explicit `layer` field on elements
Layered diagrams (User, Services, Kubernetes, Physical, ...) need a placement the model does not derive reliably (a Docker host, a VM and a Kubernetes cluster are all `node`s). Elements therefore get an optional free-text `layer` (migration 00005, `elements.layer`, empty = unassigned, max 60 chars, single line, trimmed). It is ordinary model data: it is a patch field, so it goes through drafts, diff (field-level), 3-way merge, snapshots and protected-element rules like name or technology. Snapshots written before layers existed have no `layer` key and read as unassigned (no backfill needed). One element belongs to one layer.

## ADR-041 `layers` views: layer order lives on the view
A new view kind `layers` (enum value added to `view_kind`, `views.layers text[]`) stores the ordered layer names top to bottom; different views can stack differently. Rules in `view.validateLayers`: 1..12 names, trimmed, no blanks, no duplicates ignoring case, only for this kind (a kind change away from it clears them). Membership is every element and relation of the model being shown (nesting is flattened: each element sits on the plane of its own layer); the client groups them. Elements whose layer is empty or not in the list go to a trailing "Unassigned" plane that exists only when needed (layer names match case-insensitively). Like all views it works on main and on a draft's effective model and creates no changes or versions (ADR-036).

## ADR-042 Flat stacked plans instead of CSS 3D (supersedes the first 3D rendering)
`features/layers/LayeredCanvas`: the first version rendered perspective-rotated planes with orbit / zoom; it was too fancy for the goal, which is reading flat plan diagrams stacked on top of each other and browsing them layer by layer. Now each layer is a flat lane (first layer on top) holding its cards in a grid; a layer list on the left switches layers on or off (eye) and focuses one ("only this": the other visible layers collapse to a header bar, click again or "Show all" to restore). Pure and unit-tested (`layers.ts`): grouping, lane modes, tints. Cards are real HTML, so text, tech icons, selection, keyboard focus, the context menu, diff / lint markers and filters behave as on the 2D canvas. Relations are an SVG overlay inside the scrolling content (measured relative to it, re-measured on resize / layout change); links to a collapsed layer end at its header, links to a hidden layer are not drawn; hovering or selecting a card highlights its links and dims the rest. Cards are not draggable; an element changes layer with right-click -> Move to layer, or the Layer field.

## ADR-043 Editing layers
The element form has a Layer field with suggestions (the view's layers plus those already used); the property panel shows it. In a draft's layers view the context menu adds "Move to layer" (the view's layers plus Unassigned; the current one is disabled) on elements and "Add element to <layer>" on a plane, and "Connect to..." works by clicking the target card. The view dialog has an ordered layer editor (add, move up / down, remove) with `User, Services, Kubernetes, Physical` as the default for a new layers view. `task seed` assigns layers to the sample model and creates a "Layers" view for it (existing databases keep their elements unassigned; assign layers in a draft).

## ADR-044 Projects: a many-to-many `projects` field on elements
To see "what belongs to project X" an element gets `projects text[]` (migration 00006; names, like tags). It is ordinary model data: a patch field that flows through drafts, diff, 3-way merge, snapshots (older snapshots read as empty) and protected-element rules. An element may belong to several projects (shared databases, gateways). Rules (`model.NormalizeProjects` / `ValidateProjects`): trimmed, blanks dropped, duplicates ignoring case dropped, at most 20, each a single line up to 60 characters. There is no project table: a project exists while some element names it.

## ADR-045 Project highlight reuses the canvas filter
The element panel lists the known projects; picking one sets `filter.project` in the canvas store, so the tree, the 2D canvas and the layers view all dim what is not in the project (case-insensitive match). In the layers view only the elements themselves count, not their ancestors. It is UI state, never saved with a view.

## ADR-046 Managing layers and drag & drop
Layers live on the view, so create / rename / reorder / delete are view updates (allowed to the view's creator or a maintainer, like editing the view) and need no changeset. Right-click a layer for New layer, Rename, Move up / down, Delete; right-click the empty area for New layer. Rename also records an `update` change of `layer` for every element on it in the open draft, then renames it in the view; Delete only removes the layer from the view, the elements keep their layer value and show as Unassigned until moved (the model is untouched). Names are validated in the UI (`layerNameError`: unique ignoring case, not "Unassigned", at most 12 layers / 60 characters) and by the API. Dragging a card onto another layer (HTML drag & drop, drafts only) records the same `layer` update as "Move to layer"; the menu stays as the keyboard path.

## ADR-047 `database` element kind, replicas and properties (supersedes the cylinder heuristic; the kind part is superseded by ADR-062)
The first version guessed datastores from tags and technology names; that was unreliable, so a datastore is now its own element kind `database` (migration 00008). Hierarchy like a container (parent: system, required), it can be `deployed_on` a node, and lint's deployment rule covers it. It is drawn as a cylinder (`canvas/shapes.tsx`, an SVG that stretches to the card, in the 2D canvas and the layers view). Existing containers are changed to `database` in a draft like any other edit.
`replicas` (integer 1..100, default 1) is how many instances an element stands for: more than one is drawn as stacked copies behind the card with a `x3` badge, for any kind (databases, Kubernetes workloads). Separate read-replica elements can still be modelled with ordinary elements and relations.
`properties` (jsonb, key -> value, at most 20, short single-line entries) holds free-form facts such as `ip`, `port`, `namespace`, `cluster`; the cards show `ip[:port]`. A patch replaces the whole map. Both fields are ordinary model data (drafts, diff, merge, snapshots; older snapshots read as 1 / empty).
Kubernetes needs no new kinds: cluster and namespace are nested `node`s, workloads and Services are elements inside a namespace (technology "Kubernetes ..."), all on the Kubernetes (or Infra) layer. The layers view nests the elements of one layer by their parent and draws a parent that has children on that layer as a dashed group, so a namespace shows what is inside it.

## ADR-048 Layer rules: which element classes may sit on which layers
Table `layer_rules (element_class, layers[])`, global to the model (not per view), edited by maintainers (`GET|PUT /layer-rules`, PUT replaces all). A class is an element kind (including `database`); a class without a rule is unrestricted, and an element without a layer is always allowed. Enforcement is in the changeset service (`WithLayerRules`, `model.CheckLayer`): adding an element, or an update that touches `layer`, `kind`, `tags`, `technology` or `name`, is rejected with 400 when the result sits on a disallowed layer; other edits of an element that already violates a newer rule still work, and existing data is never rewritten. The web client mirrors the check (`layerViolation`) for early feedback only: the element form shows the error, Move to layer / Add element entries are disabled, and drag & drop refuses (the target dims). Maintainers edit the rules from the Rules section of the layer list. `task seed` adds `database -> Services, Data`.

## ADR-049 Deployment field, technology search and in-place editing
"Deployed on" is a field of the element form (container, component, database), but it stays a `deployed_on` relation in the model: saving diffs the chosen nodes against the element's existing `deployed_on` relations and records the missing adds / extra deletes in the same batch as the element change (`deploymentInputs`), so it is one undo step and needs no API change. The diff always runs against the draft's whole relation set, never a view's subset. Where something runs is shown on cards (a "Docker Host" chip, `+N` for several nodes), as a "Deployed on" row in the details panel (amber "Not deployed on any node" mirrors the lint warning) and as a "Hosts" list on a node.
The technology field is a Base UI Autocomplete (`components/ui/autocomplete.tsx`): free text, with suggestions that list the technologies the model already uses first (most used first) and then a known list that all have bundled icons (`tech-icon/catalog.ts`).
Editing an element no longer opens a dialog: Edit in the details panel turns the fields into inputs with Save / Cancel (Enter saves, Escape cancels; the context menu's Edit selects the element and starts the same editor). Selecting another element or the draft becoming read-only discards the edit. Adding an element still uses a dialog; both share `ElementFields` / `useElementForm`.

## ADR-050 User management by maintainers
`GET /users` and `PUT /users/{id}/role` are maintainer-only (checked in `user.Service`). The role change runs in one transaction that locks the maintainer rows, and the service vetoes demoting the last maintainer (409), so the model can always be administered. There is no user creation or deletion: accounts still come from `task seed` until real authentication exists (superseded by ADR-059 / ADR-060). The web app shows a Users page (nav link only for maintainers; other roles see "Maintainers only") with a role select per user and a short description of each role.

## ADR-051 Version browser
`/versions` lists merged versions (summary, time, link to the changeset) and shows any version read-only: the model workspace on `GET /versions/{n}/model`, and a Changes tab that is `GET /versions/{from}/diff/{to}`, the same structured diff as a draft's (`changeset.Between` on two snapshots; base = `from`, main = `to`, never stale). By default a version is compared with the previous one; "Compare with" picks any other version, in either direction. The Model tab can highlight what changed since the compared version, with removed elements drawn as ghosts like in a draft. Merged versions never change, so the web client caches them forever.

## ADR-052 Loading, empty and error states; custom icons deferred
One `StatePanel` component is used for loading (skeleton lines), empty (a quiet card with a border beam that respects reduced motion) and error (message plus Retry) states on every page, replacing ad-hoc text. Custom technology icon upload from the M6 brief is deferred by decision: `TechIcon` keeps simple-icons, logos and the generic fallback, and the technology field only suggests technologies that have a bundled icon (ADR-049).


## ADR-053 Users vs identities (M7)
`users` holds only the internal account: stable id, name, contact email, role, `disabled_at`. Credentials live in `user_identities` (provider, issuer, subject, informational email, `last_login_at`; a password hash only for local identities). The lookup key of an identity is `(issuer, subject)` (unique), never email: `users.email` is a nullable, non-unique contact attribute (two accounts may share one; they are never merged). The local provider uses issuer `urn:archmap:local` and the normalized (trimmed, lower-case) login email as subject. Audit columns (`changesets.author_id`, `approved_by`, `merged_by`, `views.created_by`) keep referencing `users.id` only. Migration `00009_auth` moves every existing `password_hash` into a local identity.

## ADR-054 Auth provider interface; dev login replaces `X-Dev-User` (M7)
`internal/auth.Provider` has two kinds: `password` (credentials posted to `POST /auth/login`) and `redirect` (`GET /auth/{provider}/start` -> IdP -> `GET /auth/{provider}/callback`, with state / nonce / PKCE kept in `auth_flows` and a short-lived flow cookie). Every provider returns a normalized `Identity{Provider, Issuer, Subject, Email, Name, Claims}`; the login pipeline in `auth.Service` (rate limit -> provider -> resolve by issuer/subject -> provision or reject -> disabled check -> role resolution -> session) is the same for all of them, so OIDC (M15) is one more provider. Unknown identities are provisioned only when the provider allows it (`AutoProvision`, off for local and dev); otherwise the login is refused. Implementations now: `local` (email + argon2id, dummy hash for unknown users) and `dev` (passwordless sign-in as an existing local user). The stateless `X-Dev-User` header and `httpx.devAuth` are removed (supersedes the dev-auth parts of ADR-029 / ADR-034): dev login creates a normal session, so development exercises the real session and CSRF path. `config.Load` refuses `AUTH_DEV_LOGIN=true` unless `APP_ENV=development`; `APP_ENV` defaults to `production`, so a stray flag fails closed. A fake provider (`auth/authtest`, both kinds) drives the tests.

## ADR-055 Server-side sessions (M7)
A session is a row in `sessions` keyed by `sha256(token)`; the raw 32-byte random token exists only in the cookie (`__Host-archmap_session`, `Secure; HttpOnly; SameSite=Lax; Path=/`; plain `archmap_session` without `Secure` when `COOKIE_SECURE=false`, which is only allowed in development). Lax, not Strict, so the future OIDC callback (a top-level GET from the IdP) carries the flow cookie. Idle (`SESSION_IDLE_TIMEOUT`, 8h) and absolute (`SESSION_MAX_AGE`, 7d) expiry; the idle deadline slides at most once a minute. Every login creates a new token (no fixation) and drops the session the browser already had. The session middleware resolves the cookie with one query joined to `users` (`disabled_at IS NULL`), so disabling a user or changing a role applies on the very next request; disabling, password resets and password changes also delete sessions. Unlinking an identity deletes the sessions created through it (FK cascade). Expired rows are removed lazily and by an hourly sweeper.

## ADR-056 CSRF: Origin check plus a session-bound token (M7)
Two layers on every unsafe method: Go's `http.CrossOriginProtection` (Sec-Fetch-Site / Origin vs Host; also protects `POST /auth/login`, where no session exists yet), and a synchronizer token stored on the session that the client must echo in `X-CSRF-Token` (constant-time compare) on unsafe `/api/*` requests carrying a session cookie. The token is returned in the bodies of `POST /auth/login` and `GET /auth/session` and kept in memory by the web client, never in a readable cookie. A mismatch is a 403 problem with type `https://archmap.dev/problems/csrf`; the web client refetches the session and retries once.

## ADR-057 Login rate limiting (M7)
In-memory fixed-window counters per client IP (50 failures / 15 min) and per provider + normalized username (10 / 15 min), behind a `Limiter` interface with an injected clock. Only failures count; a success clears the username key. Exceeding a limit is `apperr.TooManyRequests` -> 429 with `Retry-After`. In memory is enough for one API instance (M8); a shared store can implement the same interface later. Credential failures are always the same generic 401; "disabled" and "use single sign-on" are only revealed after a correct credential check. The client IP comes from Echo's IP extractor, trusting `X-Forwarded-For` only from `TRUSTED_PROXIES`.

## ADR-058 Role source is replaceable (M7)
Roles stay on `users.role`. After an identity resolves to a user, `auth.RoleResolver` decides the effective role; M7's `StoredRoles` returns the stored role and ignores claims, so nothing a provider asserts can raise a role. M15 can add a claims / groups mapper behind the same interface. Users provisioned from an external identity start as `viewer` (`RoleResolver.Default`). Role changes otherwise only go through the maintainer-only `PUT /users/{id}/role`.

## ADR-059 No email auto-linking; break-glass maintainer (M7)
Identities are never linked by email: an unknown `(issuer, subject)` with a known email is a different account (or a refused login), never the existing user. Linking an external identity to a user (`POST /users/{id}/identities`) and unlinking (`DELETE /users/{id}/identities/{identityId}`) are explicit maintainer actions. Invariant enforced in `user.Service` inside the transaction that locks maintainer rows (it replaces ADR-050's "last maintainer" rule): at least one enabled maintainer with a local password identity must remain, so demote, disable and unlink that would break it get 409. `AUTH_LOCAL_PASSWORD=maintainers` limits password login to maintainers once SSO exists (the provider is listed as restricted, "Administrator sign-in"). `cmd/admin ensure-maintainer -email … -name …` (password read from stdin) creates the first maintainer or restores one (enabled, maintainer, new local password) straight in the database, for the first install and for recovery.

## ADR-060 User management (M7, supersedes the "no user creation" part of ADR-050)
Maintainers create users (`POST /users`: name, email, role, optional password; without one a temporary password is generated and returned once), disable / enable them (not themselves), reset local passwords (sessions revoked; the user must choose a new password at next sign-in, `password_must_change`) and view, link and unlink identities. Users change their own local password with `PUT /me/password` (other sessions revoked). While a session's password is maintainer-set, the session middleware answers every other `/api` call with 403 problem type `https://archmap.dev/problems/password-change-required` (only `/me`, `/me/password` and `/auth/*` work), so a maintainer who knows the temporary password cannot act as the user; the web app shows a non-dismissable change-password dialog. Password policy: 12 to 256 characters, no composition rules (NIST SP 800-63B). Users are never deleted: audit rows reference them. The dev seed password became `archmap-dev-password` (the old one was shorter than the policy).

## ADR-061 Cookies and redirects from strict handlers (M7)
The generated strict handler calls `Visit<Op>Response(http.ResponseWriter)` on whatever the handler returns, so `auth/transport` returns small types implementing those interfaces that set cookies (and `Location` for redirects) before writing the body. Cookies are not spec parameters (their names depend on `COOKIE_SECURE`): the httpx middleware puts the request's cookies, client IP and user agent into the context (`platform/reqinfo`), and services / auth transport read them from there. The request validator runs with `openapi3filter.NoopAuthenticationFunc`: the spec documents the cookie / CSRF schemes, enforcement lives in the middleware and services.

## ADR-062 Element `type` facet; the `database` kind is retired (M10, supersedes the kind part of ADR-047)
One database server hosts many logical databases, which the C4 hierarchy already expresses: the server is a container, each logical database a component under it. What was missing is *what kind of thing* a container or component is, so elements get a `type` separate from `kind`: `database-server`, `database`, `schema`, `cache`, `queue`, `proxy` (empty = none). The cylinder is drawn for the datastore types (database-server, database, schema) in both canvases; nothing else decides it. The `database` kind of ADR-047 is retired: migration 00010 turns those elements into containers of type `database` with the same id (decided: they keep today's meaning, the data store of a system). Historical snapshots are not rewritten; `Element.Normalized` maps the old kind when snapshots, rows and patches are read, so version diffs across the migration stay empty and open drafts still replay. The API never returns the old kind but accepts it in patches. Kind/type fit is the lint ERROR `type-kind` (`database-server` on containers; `database` on containers or components; `schema` on components; `cache` / `queue` on containers or components; `proxy` also on nodes, since reverse proxies are often modelled as infrastructure). Layer rules match a class against kind or type (the names do not overlap), so the existing `database` rule keeps meaning datastores.

## ADR-063 Ownership is model data: owners, ownerships, one owner per role (M10)
Every database / container needs an accountable owner, and changes to ownership must be reviewed and kept in history. So `owners` (team or person, contact, on-call URL) and `element_owners` (element, owner, role `owner|maintainer|oncall|escalation`) are model entities with their own change targets, not tables edited directly. Owners are not login `users`: a person can own things without an account, and a later identity-provider group mapping (M15) can link them without coupling the two (a nullable `external_ref` column is reserved, not exposed). Decided: at most one owner per (element, role). The ownership id is `uuidv5(element_id, role)`, so two drafts assigning the same role on the same element touch the same target and conflict on `owner_id` instead of both being kept; an update may only change `owner_id`. Deleting an element deletes its ownerships in the same batch; deleting an owner that is still assigned needs `cascade`. Owner names are unique ignoring case (checked when editing and by lint). Who owns a protected element is part of it: ownership changes on a protected element need the four-eyes merge of ADR-023.

## ADR-064 Inheritance is computed on the server (M10)
Owners (per role), environment and deployment are inherited: an element's effective value is its own, else its nearest ancestor's (decided for environment, so a logical database inside a prod server counts as prod). Overriding is assigning the value on the child; there is no explicit "stop inheriting" marker. `model.ComputeEffective(snapshot)` is the single implementation: every model read (main, drafts, versions, views) returns `Element.effective` with the value and the element it comes from, and lint and the `unowned` view call the same function. A view shows a subset, but its effective values are computed on the whole model. The web client only renders them (no client-side inheritance rules).

## ADR-065 Operational fields (M10)
Elements get `environment` (prod / staging / dev / unset), `lifecycle` (active / deprecated / planned; elements stored earlier read as active), `criticality` (low / medium / high / critical / unset), `runbook_url` and `docs_url` (http(s) URLs) and `last_reviewed_at` (a date). They are ordinary patch fields: drafts, field-level diff, 3-way merge, snapshots (missing in older snapshots → defaults). Marking an element reviewed is a change in a draft like any other edit, so reviews are versioned too.

## ADR-066 Lint rules for ownership, lifecycle and reviews (M10)
`deployment` (WARN) now uses effective deployment, so logical databases under a deployed server are no longer flagged. New: `owner-required` (ERROR, blocks merge) for elements whose effective environment is prod without an effective `owner`; `stale-review` (WARN) for reviews older than `LINT_REVIEW_MAX_AGE` (default 180 days), and for never-reviewed elements only when they run in prod (decided, to avoid a flood of warnings on existing models); `deprecated-dependency` (WARN) when an active element uses or is deployed on a deprecated one; `type-kind` and `ownership` (ERROR). Rules stay pure functions of a snapshot; the time-dependent one gets `lint.Options` (clock and age), wired from config through `changeset.WithLintOptions`. Nothing is prod until someone marks it, so existing models get no new errors from the migration.

## ADR-067 Human-owned fields for future connector sync (M10)
`environment`, `lifecycle` and all ownership (owners and ownerships) are human-owned. A connector that syncs elements from external systems (M12) may create elements and update technical fields (technology, properties, replicas, deployment), but must never write these, because only people know who is accountable and what is in production. The list is `model.HumanOwnedFields` (plus the owner / ownership targets) so M12 can enforce it in code and tests rather than by convention.

## ADR-068 An entity added on both sides is merged field by field (M10)
Before M10, an id present in mine and theirs but not in the base meant "theirs wins" silently; with random ids this never happened. Deterministic ownership ids make it normal, so `Merge3` now treats such an entity as a field-level 3-way merge against an empty base: identical values merge, different values are a `field` conflict (resolved with mine / theirs like any other). Ownerships whose element or owner the merge removed are dangling references, handled by the existing resolution flow (restore the referenced entity from the chosen side, or drop the assignment).

## ADR-069 Owners can be users or groups (amends ADR-063)
Owners stay model data (versioned through drafts), but an owner may now point at a principal: kind `user` (a login user) or `group` (an app-managed group, ADR-070), next to the free `team` / `person` kinds for owners without accounts. The owner of a principal has a deterministic id, `uuidv5(principal_id)`, so a user or group has at most one owner entity. Picking the same user twice reuses it, and two drafts that both introduce it merge without a conflict (identical add/add, ADR-068). The web picker hides the owner entity: choosing a user or group without one adds the owner and the ownership in one batch. The owner keeps the name it was created with (history, versions); the web shows the principal's live name and state from `GET /directory` (a group or user missing from it is shown as deleted / disabled with the stored name), so renames show everywhere without threading the directory through every model read. An effective owner that is a disabled user or a deleted group is the lint WARN `owner-inactive`; `owner-required` is unchanged. Linking checks the principal exists and is usable at that time.

## ADR-070 Groups are account administration
Groups (`groups`, `group_members`) are managed by maintainers on the Users page, like roles: they are not model data, not versioned, and not reviewed. Assigning a group as an element's owner is still a reviewed draft change. Group names are unique ignoring case; deleting a group soft-deletes it, so owners that point at it keep a name and lint warns. Every signed-in user can read a directory of users (name, email, disabled) and groups (name, description, member count) to pick owners; roles are not exposed. Identity-provider groups (M15) can later fill a group's members.

## ADR-071 Focused canvas: double-click drills down (amends ADR-026)
Large models do not fit one canvas. Like C4 tools (IcePanel, Structurizr), the canvas can focus one element: it shows the element's subtree plus the outside elements related to it (`uses` and `deployed_on`). Each outside end is lifted to its highest ancestor that does not contain the focus, the same rule as a server-side container view (`view.Compute`), so context stays at the level of systems and nodes. Context cards are muted, marked "External" and cannot expand. Double-click now drills into an element with children (expanding stays on the chevron and the toolbar); `F` focuses the selection, `Esc` goes up one level, and the breadcrumb in the canvas toolbar island goes anywhere up. The focus lives in the URL (`?focus=`), so it is shareable and the browser's back button works. It is never written to a view's layout: the store keeps the view's layout aside and remembers each focus's expand state and drags only while the page is open. "Save as view" turns a focused system / container into a container / component view. For large models: ELK runs in a web worker, React Flow renders only visible elements, edge aggregation resolves nearest visible ancestors once per element, and "Expand all" opens one level at a time above 300 elements.

## ADR-072 Configurable review policy: a direct edit is an auto-merged changeset (amends ADR-018, ADR-022, ADR-033)
For personal and small-team use the draft / submit / approve / merge flow is too heavy. A workspace-wide setting (`settings.review_policy`, one row, maintainers only, not versioned) chooses `required` (default, unchanged behaviour) or `direct`. Under `direct`, editors edit main in place. Each save goes to `POST /model/changes`. That request runs under the main lock: it builds the batch on the current main with the same validation as drafts, stores it as a changeset, and merges it at once as a new version (always a fast-forward). So history, diffs, versions and the version browser need no second write path.

Governance stays:
- An edit that adds lint errors (compared to main's own) is kept as a normal draft to fix. A draft in review cannot be edited, so it does not go there.
- An edit that touches a protected element is submitted for review by an independent maintainer (ADR-023).
- Only maintainers may change the protected flag.

Other rules:
- Direct changesets have `kind = 'direct'` and are not listed with the drafts.
- Undo on main is `POST /model/changes/{id}/revert`: a new direct edit computed by merging the edit's version back (`Merge3(base = v, mine = v-1, theirs = main)`). It is refused when someone changed the same fields since, or when the edit was already undone. Only the author or a maintainer may undo; `changesets.reverts` links the undo to the edit.
- Concurrent edits are field-level last-writer-wins, like IcePanel. The web refreshes main when a new version appears (polling every 15 s and on focus); SSE / presence is later work.
- Every save is a version. The version list folds consecutive direct edits by one person into one row. Snapshots are full copies today (ADR-020); delta snapshots are the escape hatch if this grows too large.
- `MERGE_ALLOW_SELF` still only affects the review flow.
